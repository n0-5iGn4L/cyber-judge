# 事件争议型

## 事件底稿

用不依赖圈内知识的梗概交代主体、触发材料、主要进展和当前状态。必要时画时间线和角色关系；事件发生、发言、报道与更新时间分别处理，不为凑图补造日期或关系。

将已确认事实、当事人主张、分析推断和未知分别写清。对截图、切片、报道标题核查上下文、来源与指向，不能把第三方标题当作当事人承认。

## 争论点选择

先列出调研中发现的全部实质争论点，再按问题归并并决定展开深度。不要按预设栏目截断争议；常见问题包括：行为是否发生、语境是否完整、原因是否成立、是否违反明确义务、应承担何种责任、回应或补救是否充分。无需凑齐所有栏目。

产品或技术安全事件尤其区分：

1. 实际观察或报告了什么失效。
2. 哪种机制可以解释失效，替代解释如何排除。
3. 适用工况与影响范围是否可推广。
4. 现在应采取什么行动，以及最终责任需要什么证据。

测试比较核对样品、批次、状态、安装、加载和测量方法、校准、完整记录与判据。几个样本共用同一方法，不等于几次独立验证。方法非标不自动无效，标准合格也不自动覆盖所有现实场景。

## 局部裁定与行动

先逐项裁定，再形成整体意见。观察到异常可以支持调查与适度预防，不必等到全部责任明确才采取行动；反过来，启动调查、提供升级或补救，不自动证明某方已被认定违法或自认全部责任。

说明各方提出什么主张、掌握什么资料，因而负有什么解释责任。不要要求普通质疑者先完成全部技术鉴定，才承认其安全问题值得回答。

真实事件可以引出公共讨论，但应指出个案的代表性边界。不要从一个纠纷直接推导整个行业、人群或制度的确定结论。
